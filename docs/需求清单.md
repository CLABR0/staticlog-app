## 三、当前阻塞项

### ~~C1 · 「自动识别橘子系统」缺判据~~ → 已解决

**已确认判据（2026-11-03 由设备方给出）**：

| 软件版本号前两位 | 对应代数 |
|---|---|
| **16** | 第 6 代（橘子6） |
| **17** | 第 7 代（橘子7 / OS7） |

版本串形如 `PD2408_A_16.9.1`，解析时要跳过型号前缀（取 `_` 后那段），
不能直接取字符串前两位（那是 `PD`）。

读取顺序（第一条能解析出的采用）：`ro.vivo.os.build.display.id` → `ro.vivo.os.version`
→ `ro.vivo.product.version` → `ro.rom.version` → `ro.originos.version` → `ro.vivo.os.name`
→ `ro.system.build.version.incremental` → `Build.DISPLAY` → `Build.VERSION.INCREMENTAL` → `Build.FINGERPRINT`。

**真机排查入口**：设置 →「版本诊断」，逐条显示属性名与原始值，不需要 logcat。

两代资源包的文件名都是 `66127-7741-*`，面向**同一内核**（6.6.127 + 尾号 7741），
区别在流程代数：

| 代数 | 文件组成 | 方式 |
|---|---|---|
| 第 6 代 | `zt_run` + `zt_su` + `zt_fanout.zte` + `zt_su.zte` | 写命令文件 + `zt_su --daemon` 守护 |
| 第 7 代 | `zt_run` + `zt_fanout.zte` + `zt_prep.zte` | 直接 insmod 内核模块 |

所以「这台设备该用第几代」**无法从内核 / SDK / 机型推导**。

当前判定链（五层）：

| 优先级 | 依据 | 算不算「已确认」 |
|---|---|---|
| A | 历史成功记录（上次某代真跑到 uid=0 才写） | 是 |
| B | **软件版本号**：16 → 第6代，17 → 第7代 | 是 |
| C | 已验证指纹规则（完整 `Build.FINGERPRINT` 精确匹配，**空表**） | 是 |
| D | **失败规避**：上一次跑失败的那一代，本轮改试另一代 | 否 |
| E | 兜底取较新代数，界面标「未确认」 | 否 |

失败规避已实现：`PayloadRunner` 四个失败出口都会写失败记录，下次自动换另一代；
任一成功则清掉失败记录。**不会在本次执行里自动重跑**（避免两次副作用）。

**当前状态**：真机实测仍判不出（显示兜底）。下一步用「版本诊断」读出实际值再定属性名。
若版本号读不到，会自动落到下一层（指纹 / 失败规避 / 兜底），不会崩。
排查时看界面摘要的来源标记：`第6代·版本号 · …` 表示已按版本号判定。
